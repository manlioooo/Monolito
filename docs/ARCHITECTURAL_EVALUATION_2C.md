# Tarea 2c - Evaluación arquitectónica

Para una librería académica administrada por un equipo pequeño, el monolito server-side es una elección adecuada. El dominio necesita autenticación, catálogo, relaciones normalizadas, imágenes y operaciones CRUD, pero no presenta equipos autónomos, cargas radicalmente distintas ni ciclos de despliegue independientes. Express, EJS y PostgreSQL permiten entregar esas funciones como una unidad coherente. El navegador envía formularios y recibe HTML; desaparecen la API pública, el manejo duplicado de modelos en frontend y backend y buena parte de la complejidad de estado del cliente.

La ventaja operativa es clara. Se instala un proceso Node, una base PostgreSQL y un reverse proxy. Un único archivo de variables configura la conexión, sesiones y prefijo. El diagnóstico también es lineal: una solicitud atraviesa NGINX, middleware, ruta, servicio, PostgreSQL y plantilla. En una solución desacoplada por componentes, un frontend independiente necesitaría una API, CORS, versionado de contratos, autenticación entre orígenes y dos pipelines. Esa separación podría mejorar la experiencia de interfaces muy interactivas o permitir clientes móviles, pero ninguna de esas condiciones forma parte del alcance actual.

Frente a microservicios, la diferencia es todavía mayor. Separar identidad, catálogo, inventario e imágenes exigiría descubrimiento, comunicación remota, observabilidad distribuida, reintentos, manejo de fallos parciales, secretos por servicio y posiblemente consistencia eventual. La operación consumiría más esfuerzo que la lógica del negocio. PostgreSQL ofrece transacciones simples para guardar un libro junto con autores y géneros; distribuir esa operación obligaría a introducir sagas o compensaciones. Para una persona o un equipo de clase, el coste no se justifica.

El monolito no elimina la necesidad de diseño interno. Las rutas sólo coordinan HTTP, los servicios concentran operaciones, el middleware aplica controles transversales, EJS presenta y PostgreSQL protege invariantes. Esta modularidad reduce el coste de mantenimiento y deja fronteras que podrían extraerse más adelante. No obstante, todos los módulos se despliegan y escalan juntos. Un cambio pequeño requiere publicar la aplicación completa y una fuga de memoria puede afectar todas las funciones. El filesystem local para imágenes también dificulta ejecutar varias réplicas sin almacenamiento compartido.

En seguridad, una única superficie desplegable reduce credenciales y enlaces internos, pero concentra impacto: comprometer el proceso concede acceso a todo lo que permita `library_app`. Las consultas parametrizadas, la autorización centralizada, CSRF, cookies seguras y privilegios PostgreSQL limitados reducen ese riesgo. Microservicios podrían aplicar credenciales más estrechas por dominio, aunque añadirían autenticación servicio-a-servicio y más configuraciones susceptibles a errores.

La escalabilidad inicial se resuelve verticalmente y con índices, pool, paginación futura y caché. Si las imágenes crecieran, el primer paso razonable sería moverlas a Cloud Storage/CDN, no dividir todo el sistema. Una API separada se justificaría con aplicación móvil o múltiples clientes. Microservicios sólo tendrían sentido con alto tráfico desigual, requisitos de disponibilidad independientes y varios equipos responsables de dominios distintos. Hasta entonces, el monolito modular ofrece el mejor equilibrio entre simplicidad, integridad, seguridad comprensible y velocidad de entrega, aceptando conscientemente que su unidad de fallo y despliegue es más grande.
